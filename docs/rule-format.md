# 规则格式规范

## 规则结构

每条规则是一个 YAML 头 + Markdown 正文的结构化文件。

```yaml
---
id: rule-2026-06-17-001
source: "真实来源标注，如: 李景怡线·实战训练"
scenario: "触发场景描述，如: 她说'喜欢上你了怎么办'后跟害羞/啰嗦/自嘲"
root_cause: "根因分析，如: 把掩护信号当成主体信号处理"
fix: "修复方案，必须是可执行的指令"
applies_to:
  - 分类标签1     # 用于匹配和检索
  - 分类标签2
hit_count: 3      # 命中次数，决定规则优先级
merged_with: null # 如果已合并，指向被合并的规则ID
created_at: "2026-06-17T07:00:00Z"
---
```

规则正文保留 Markdown 格式（方便人类阅读和管理）。

## ID 生成规则

```
rule-YYYY-MM-DD-NNN
```

- YYYY-MM-DD: 创建日期
- NNN: 当天递增序号（从 001 开始）

## 规则优先级

当多条规则同时适用于同一场景时：

1. **命中次数** — 最高的优先
2. **严重度** — critical > high > medium > low
3. **更新时间** — 最近的优先
4. **来源标注** — 用户实战修正 > 知识库提取 > 默认规则

## 合并规则

当两条规则根因高度相似时，会触发合并：

```yaml
---
id: rule-2026-06-17-001
hit_count: 5
fix: "原修复方案 | 增强: 新修复方案"  # 合并后的增强版
applies_to:
  - IOI识别     # 合并后的标签合集
  - ASD破解
similar_rules:
  - rule-2026-06-17-003  # 被合并的规则
---

已被合并的规则标记为：

```yaml
---
id: rule-2026-06-17-003
merged_with: "rule-2026-06-17-001"
---
```

被合并的规则不参与匹配，但保留在库中供追溯。
